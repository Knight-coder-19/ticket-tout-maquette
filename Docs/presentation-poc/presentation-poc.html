Spécimen

Le projet

Un budget dans la poche,
un paiement en trois secondes

  • Le Ministère veut moderniser les avantages salariés dématérialisés : un budget crédité par l'employeur, dépensé chez des commerces partenaires référencés.
  • Trois acteurs — le salarié, le partenaire commerçant, l'administration.
  • Aujourd'hui : du papier, des lourdeurs de gestion. Demain : une carte, un geste.

Ce POC, précisément

Le parcours complet tourne,
de bout en bout

Un démonstrateur fonctionnel — pas des maquettes. Aucune valeur réelle : une mention de simulation figure sur chaque écran affichant un montant.

  • Périmètre : les 3 espaces + une API + une base de données + un jeu de données de démonstration.
  • But : montrer que le dispositif marche et que les règles sensibles sont tenues — pas seulement décrites.

La démonstration · 3

Salarié —
payer

  • Le salarié fixe le montant à l'émission — pas le partenaire à la caisse.
  • Code à usage unique, valable 5 minutes au plus, compte à rebours, régénération en un geste, état « expiré ».
  • Le vrai code est signé par le serveur (Ed25519).

Sous le capot

Architecture d'ensemble

Frontend

Next.js 16 / React 19 / TypeScript. Les 3 espaces, CSS pur, polices auto-hébergées, icônes et graphiques maison.

Backend

Rust / Axum / PostgreSQL 16. Logique métier isolée du transport HTTP, registre comptable en base.

Contrat d'API

Euros décimaux sur le fil, snake_case, pagination par curseur, enveloppe d'erreur stable, session par cookie HttpOnly.

Principe

Le back est la seule autorité — soldes, signatures, registre. Le front affiche, ne calcule jamais.

Sous le capot

Le flux de paiement

Le salarié autorise un montant → le back réserve les fonds (held) et signe le QR (Ed25519).

Le partenaire scanne le QR, ou saisit le code court à la main.

Le back vérifie l'expiration contre sa propre horloge et le double usage, puis écrit au registre : débit salarié / crédit partenaire.

token_jti est unique en base → un double scan renvoie la même transaction, ne débite jamais deux fois.

Sécurité & conformité — déjà tenu

Les règles sont dans le code,
pas seulement dans la doc

  • Registre en ajout seulGaranti par PostgreSQL (ni UPDATE ni DELETE) + chaîne de hachage vérifiable.
  • Solde jamais négatifUn débit supérieur au disponible est refusé proprement, avec un message qui dit pourquoi.
  • QR signé, usage unique, 5 minUn code périmé est inutilisable, un rejeu ne double-débite pas.
  • SessionCookie HttpOnly, jeton haché en base, contrôle de rôle dans la signature des routes.
  • RGAA AAContrastes vérifiés par script, navigation clavier, alternatives lecteur d'écran.
  • SouverainetéZéro service tiers — l'application démarre sur une machine hors ligne.
