## 2. `migrations/`

The schema fits in **a single file**, `migrations/0001_schema.sql`, in line with the task
distribution (`TASK-DISTRIBUTION-BACKEND.md` §4.1). Splitting into twelve migrations only makes
sense once the schema has been deployed somewhere: as long as nothing has run, a single file is
easier to review and to replay. `sqlx` refuses any migration whose fingerprint changes after
execution, so from the first deployment onwards, corrections go through `0002_*.sql`, `0003_*.sql`,
and so on.

| File | Contents | Prio |
|---|---|---|
| `0001_schema.sql` | Extensions (`citext`, `pgcrypto`), the 13 enums, the 16 tables in dependency order, the `CHECK` constraints, the partial unique indexes (`uq_active_employment`, `uq_active_short_code`, `uq_employer_ref`, the two on `partner_highlights`, `uq_batch_file`), the `forbid_mutation()` function and its triggers on `ledger_entries`, `ledger_operations` and `audit_log`, the `cartepro_app` role with its `GRANT`/`REVOKE`, and the insertion of the `MINISTRY_ISSUANCE` and `CLOSURE_FORFEIT` system accounts. | P0 |

> **Watch out for the `REVOKE` statements:** once they are in place, migrations must run under a role
> different from `cartepro_app`. Hence the two `DATABASE_URL` values in §10.
>
> **City reference data:** the insertion is absent until open question 1 of the dictionary (French or
> Beninese reference list) is settled.

### 3.3 `ledger/` — the critical module

**The only place in the code that writes to `accounts`, `ledger_operations` and `ledger_entries`.**
To be written first and tested before anything else.

| File | Expected contents | Prio |
|---|---|---|
| `mod.rs` | See the signatures below. | P0 |
| `hash.rs` | `const GENESIS_HASH: [u8; 32] = [0; 32];` and `fn entry_hash(seq, operation_id, account_id, direction, amount, recorded_at, prev_hash) -> [u8; 32]`. **Canonical serialisation documented in a comment**: any later change invalidates the existing chain. | P0 |
| `balance.rs` | `recompute_balance(conn, AccountId) -> Money`, `recompute_held(conn, AccountId) -> Money`, `verify_chain(conn, from_seq) -> Result<(), u64>` returning the first inconsistent `seq`. Used by the tests, the worker and `/admin/audit/verify`. | P0 |
| `repo.rs` | The SQL queries. No business rule. | P0 |

```rust
pub struct Posting {
    pub debit: AccountId,
    pub credit: AccountId,
    pub amount: Money,
    pub occurred_at: DateTime<Utc>,
    pub memo: Option<String>,
    pub created_by: Option<UserId>,
}

/// Global lock serialising the chaining. To be taken BEFORE any account lock.
pub async fn lock_chain(tx: &mut PgTransaction<'_>) -> Result<(), LedgerError>;

/// SELECT ... FOR UPDATE on the account.
pub async fn lock_account(tx: &mut PgTransaction<'_>, id: AccountId)
    -> Result<Account, LedgerError>;

/// THE single entry point. Creates the operation, the 2 chained entries,
/// updates the balance caches. Checks debit != credit and amount > 0.
pub async fn post_operation(
    tx: &mut PgTransaction<'_>,
    kind: OperationKind,
    posting: Posting,
) -> Result<LedgerOperation, LedgerError>;

/// Reserves funds (balance_held += amount). Fails if the available balance is insufficient.
pub async fn place_hold(tx: &mut PgTransaction<'_>, id: AccountId, amount: Money)
    -> Result<(), LedgerError>;

/// Releases a reservation.
pub async fn release_hold(tx: &mut PgTransaction<'_>, id: AccountId, amount: Money)
    -> Result<(), LedgerError>;
```

> `post_operation` never takes a `PgPool`, only an in-flight transaction. That is what guarantees it
> cannot run outside the caller's lock.

Three cases to distinguish in `settle`'s errors; the offline client depends on them:

| Situation | Return |
|---|---|
| same partner, same `jti`, already settled | `Ok(payment)` — the front end removes the line from its queue |
| another partner consumed the token | `Err(TokenAlreadyUsed)` — the front end reports it |
| token expired server-side | `Err(TokenExpired)` — the front end reports it |

```rust
// core/src/partners/highlights.rs  — A2

/// Places a highlight. Refuses if the partner is not `approved`
/// (HighlightNotEligible) or if it is already highlighted at this placement
/// (HighlightDuplicate). Writes to audit_log. position = None -> append at the end.
pub async fn add(
    tx: &mut PgTransaction<'_>,
    admin: UserId,
    partner: PartnerId,
    placement: HighlightPlacement,
    position: Option<i32>,
) -> Result<Highlight, PartnerError>;

/// Removes a highlight: sets removed_at, NEVER deletes the row (R6).
/// Writes to audit_log.
pub async fn remove(tx: &mut PgTransaction<'_>, admin: UserId, id: HighlightId)
    -> Result<(), PartnerError>;

/// Reorders a whole placement. Receives the complete list of ids
/// in the desired order. Since positions are under a partial unique index,
/// write in two passes (shift out of range, then reassign) or defer
/// the constraint for the duration of the transaction.
pub async fn reorder(
    tx: &mut PgTransaction<'_>,
    admin: UserId,
    placement: HighlightPlacement,
    ordered: &[HighlightId],
) -> Result<(), PartnerError>;

/// Read. `only_approved` is always true in practice: a partner
/// suspended after being highlighted must no longer appear.
pub async fn list(
    conn: &mut PgConnection,
    placement: HighlightPlacement,
) -> Result<Vec<HighlightWithPartner>, PartnerError>;
```

> **The `reorder` trap:** the partial unique index on `(placement, position)` forbids two rows at the
> same position, including transiently during a swap. First shift the positions concerned out of the
> range in use (into the negatives, for instance), then reassign. A dedicated test for swapping two
> neighbours.
>
> **The `list` trap:** a partner highlighted then suspended would stay on display if the join does
> not filter on `status = 'approved'`. The filter belongs in the query, not in the calling code.

### 4.4 `dto/`

One file per space: `public.rs`, `employee.rs`, `partner.rs`, `admin.rs`, `catalog.rs`,
`integration.rs`. This is for the architecture.

Each contains the request and response structures, with `Serialize`/`Deserialize`,
`utoipa::ToSchema`, and `impl From<DomainType> for ResponseDto`.

**Rule:** `core` types are never serialised directly. A DTO is an exposure decision, not a shortcut.
That avoids leaking an internal field the day it is added to the domain.

**`dto/public.rs` deserves particular vigilance (rule R9).** It contains a single type,
`PublicPartner`, each field of which is an explicit decision. Never add a `#[serde(flatten)]` to it
and never reuse `CatalogItem`: that is how an unwanted field would leak.

Amounts are always in decimal euros, two decimals at most: `"amount": 456.56`. Conversion to the
integer cents of storage is done by `Money`, never in a DTO or a handler: no `* 100` or `/ 100` must
appear anywhere other than in `core/src/money.rs`.

Imposed handler shape, without exception:

```rust
async fn settle_payment(
    AuthUser(partner): AuthUser<Partner>,
    State(app): State<AppState>,
    ValidatedJson(body): ValidatedJson<SettleRequest>,
) -> Result<Json<PaymentResponse>, ApiError> {
    let mut tx = app.db.begin().await?;
    let payment = payments::settle(
        &mut tx, &*app.clock, &app.config,
        partner.into(), body.jti, body.scanned_at,
    ).await?;
    tx.commit().await?;
    Ok(Json(payment.into()))
}
```

The resynchronisation batch is the only special case: each line in its own transaction, one status
per item. A failing line never brings down the batch.

## 9. Suggested filling order

```
1.  migrations/0001_schema.sql                 then `cargo sqlx migrate run`
2.  core: ids, money, clock, error, config
3.  core/ledger: hash, repo, mod, balance
4.  crates/tests/tests/invariants.rs                       <- do not move on until this passes
5.  core/crypto: password, token_sig (Ed25519), short_code
6.  core/identity + api/extractors/auth.rs
7.  core/payments: authorize, settle
8.  tests/payments_flow.rs, tests/degraded_mode.rs
9.  api: state, error, routes/auth, routes/employee, routes/partner
10. core/directory, core/partners (registration, review, catalog) + routes
11. core/funding: topup then batch
12. core/partners/highlights + routes admin + routes/public   <- A2, A3
13. tests/public_surface.rs
14. core/reporting + routes/admin (dashboard with the online_partners block)
15. core/corrections, api/routes/integration
16. worker
17. P1 middlewares, deploy
```

Step 4 is the checkpoint. A ledger whose invariants are not proven makes everything built on top of
it worthless.
