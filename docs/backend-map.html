CartePro Backend Map

Ninety files, and for each one the only question worth asking: what would the application be missing if it were not there? The repository's file-guide.md says what each file contains; this page says why it exists, and where the code actually stands today.

S Sèdjro G Giscard

crates/core

The domain. The ledger, payments, identity, the catalogue. It knows nothing of HTTP, of cookies, or of status codes.

No axum type here. That is rule R1, and it is what makes the domain testable without a server.

crates/api

The HTTP layer. It turns a request into a domain call, a domain error into a status code, a domain type into JSON.

No business rule here. A handler longer than fifteen lines has taken a decision that is not its own.

crates/worker

Time. Everything that has to happen without anyone clicking: token expiry, chain verification.

A separate binary from the API: it can die without interrupting a single payment.

backend/

The root: what makes the project reproducible

None of these files run anything. They guarantee that the same source produces the same binary on both developers' machines and in CI.

Cargo.toml

Declares the workspace and centralises versions in [workspace.dependencies]. Without that, two crates could compile against two versions of sqlx, and a PgPool from one would not be a PgPool to the other.

Gwritten
rust-toolchain.toml

Pins the compiler version. Not a convenience: a new rustc that hardens one lint turns a warning into an error, and CI breaks without a single line having changed.

Gwritten
.env.example

The exhaustive list of what the application expects from its environment, secrets included — named, never filled in. This is the file you read to know what must be prepared before starting.

Gwritten
.sqlx/

Cache of compile-time-checked queries, produced by cargo sqlx prepare. Empty today: we chose runtime-checked queries so that no build ever requires a reachable database.

backend/migrations/

The schema: half the guarantees live here

The easy mistake is to read these files as a description of tables. They carry rules the Rust code cannot hold on its own, because those rules must survive a concurrent request and a direct connection through psql.

0001_schema.sql

Thirteen enumerations, eighteen tables, and above all three families of guard rail: the CHECK constraints that forbid a negative balance or a hold larger than the balance, the partial unique indexes that forbid two active employments for one person, and the forbid_mutation() triggers that refuse any UPDATE on the ledger — including from the database owner. That is the second layer: the code may be wrong, the database catches it.

Swritten
0002_cities.sql

The town reference data. A physical merchant must declare a town and the catalogue filters on it; without reference data the field would be free text, "Lyon" and "lyon" would be two towns, and the filter would never return anything trustworthy.

Swritten

backend/crates/core/src/

The foundation: the types everything else handles

Six files, written first because everything depends on them. Each removes a whole class of bug by making it impossible to write rather than by testing for it.

lib.rs

The list of modules, and nothing else. Frozen in the first hour with every module declared: that is what lets two people add files all night without ever producing a merge conflict on this one.

Gwritten
ids.rs

A distinct type per identifier, generated by a macro. In a schema where absolutely everything is a UUID, passing a PartnerId where an AccountId is expected is the easiest mistake in the project and the hardest to spot in review. Here, it does not compile.

Swritten
money.rs

The only place in the program that knows a euro is one hundred cents. No * 100 or / 100 may exist anywhere else. The field is private and the constructor rejects negatives, so a negative amount cannot be produced by accident — and floating point, which has neither exact equality nor a canonical serialisation, never touches a money path.

Swritten
clock.rs

Time treated as an injected dependency rather than a system call. FixedClock is what makes it possible to test a five-minute token expiry without waiting five minutes, and to prove that a stale token is refused.

Swritten
error.rs

The error vocabulary shared by the whole domain. Its value shows downstream: api has exactly one type to translate into an HTTP response, and the mapping table lives in one place.

Swritten
config.rs

Durations and parameters — token TTL, resynchronisation window, closure grace period. core never reads the environment itself: api builds the configuration and injects it, which lets a test build a different one.

Gwritten

backend/crates/core/src/ledger/

The ledger: the only door money is written through

No other module may write to accounts, ledger_operations or ledger_entries. That exclusivity is what makes the nine invariants provable: there is only one path to check.

ledger/mod.rs

The five entry points of the money system — lock_chain, lock_account, post_operation, place_hold, release_hold — and the types they handle. post_operation never accepts a connection pool, only an open transaction: that is what guarantees it cannot run outside its caller's lock.

Swritten
ledger/hash.rs

The fingerprint of an entry, and therefore the chaining. Each entry carries the digest of the one before it: rewriting a past row would force every following digest to be recomputed, which the database triggers forbid. That is what makes tampering detectable, not merely difficult.

Swritten
ledger/repo.rs

The queries, with not one business decision. The balance guards do live here, though — inside the WHERE clause, never in an if beforehand: between a checking read and the write, another transaction slips through, and the check would have protected nothing.

Swritten
ledger/balance.rs

The read-back. Recomputes a balance from the entries, recomputes holds from the active tokens, and replays the hash chain to report the first inconsistent sequence number. This is what feeds the invariant tests and the /admin/audit/verify route: the system can say whether it contradicts itself.

Swritten

Why the balance is both stored and recomputable. accounts.balance_settled is a cache: reading a balance must not sum ten thousand entries. The ledger remains the truth. balance.rs exists precisely to prove the two agree — and if they ever diverge, the cache is the one that is wrong, which means some transaction was not atomic.

backend/crates/core/src/crypto/

Cryptography: three unrelated uses

Grouped by technique rather than by feature, which is why one file serves signing in and another serves offline payment.

crypto/password.rs

Argon2id. Passwords are never stored, only their digest, and the function is deliberately slow so that a stolen database stays expensive to exploit.

Gto write
crypto/token_sig.rs

Ed25519 signing of payment tokens. The asymmetric choice is the key to the whole degraded mode: the merchant must be able to verify a QR code offline with the public key alone. An HMAC would force them to hold the server's secret, and therefore the means to forge tokens.

Sto write
crypto/short_code.rs

The fallback code typed by hand when the camera cannot read the QR. Its alphabet excludes 0, O, 1, I and l, because it gets read aloud across a counter — a usability constraint, not a security one.

Sto write

backend/crates/core/src/payments/

Payment: issue a token, then settle it

Two moments separated in time, sometimes by several minutes, sometimes by a network outage. The whole difficulty of the project lives there.

payments/authorize.rs

Issues a token and holds the funds. The hold is what stops an employee from generating two QR codes each covering their entire balance: the second fails because the first already immobilised the money, even though no payment has happened yet.

Sto write
payments/settle.rs

Settles a token. The order of operations is the protection: idempotency first — replaying the same settlement returns the same payment instead of an error, which the merchant's offline queue depends on — then the locks, then and only then the checks, then the write. A balance check placed before the lock protects nothing.

Sto write
payments/repo.rs

Queries over tokens and payments, including locking a token and consuming it. Kept apart from settle.rs so the protective sequence reads in one piece, without SQL in the middle.

Sto write
payments/mod.rs

The payment domain types — token, status, entry mode — and the error vocabulary that distinguishes the three cases the offline client needs: already settled by me, consumed by someone else, expired.

Sto write
payments/expire.rs

Moves lapsed tokens to expired and releases their holds. Without this sweep, a QR code generated and never presented would freeze money indefinitely. With the worker cut, expiry will happen lazily on each balance read.

Sto write

backend/crates/core/src/identity/ · directory/

Who the user is, and which account they hold

identity answers "who is speaking", directory answers "which account that is". Two different questions, and conflating them is what produces authorisation holes.

identity/

identity/login.rs

Verifies the password even when the user does not exist, by comparing against a dummy digest. Without that precaution, response time would reveal which accounts exist, and the roster of civil servants would be enumerable.

Gto write
identity/session.rs

Creating, validating and revoking sessions. The token is hashed in the database; the clear value lives only in the browser cookie. A stolen database therefore lets nobody open a session as anyone.

Gto write
identity/repo.rs · mod.rs

Queries over users and sessions, and the AuthenticatedUser type the HTTP extractor builds and handlers receive.

Gto write

directory/

directory/employees.rs

Creates the employee and their account in the order the foreign-key cycle imposes, and resolves a staff number to an account. That last function is the entry point for top-ups and for the HR-system endpoint: it is how an employer designates a member of staff without knowing our internal identifiers.

Gto write
directory/employers.rs

The register of employing administrations. This is identity territory, not money territory: modification is allowed here, unlike in the ledger.

Gto write
directory/cities.rs

Read-only access to the town reference data, served to the merchant registration form and to the catalogue filter alike. One source so the two lists can never drift apart.

Gto write
directory/employment.rs

Ending an employment and forfeiting the residual balance to the CLOSURE_FORFEIT system account once the grace period has passed. Designed, documented, not implemented: someone leaving the civil service is a real case, but not one that demonstrates well in a defence.

Gcut
directory/repo.rs · mod.rs

Queries and types for the register.

Gto write

backend/crates/core/src/partners/

Merchants: from application to shop window

A merchant passes through four states and every transition is an administrative decision. The module follows that life cycle, one file per stage.

partners/registration.rs

The application: creates the user, the account and the merchant in pending status. Validates that service mode and town agree — a physical shop with no town would appear in no catalogue filter and would therefore be invisible forever.

Gto write
partners/review.rs

Approval or rejection by an administrator, traced in the audit log. This is what gives the approved status its meaning, and settlement depends on it: an unapproved merchant cannot receive public money.

Gto write
partners/catalog.rs

Paginated search. Pagination is keyset and never by OFFSET: over a list that keeps changing, an OFFSET makes rows skip or repeat between pages, and its cost grows with the page requested.

Gto write
partners/highlights.rs

The features chosen by the ministry. Removing a feature records a date and never deletes the row — the trace of who put which shop in the window, and when, is exactly what an audit can ask for.

Gto write
partners/repo.rs

Holds approved_account, the function settle calls to obtain the account to credit — and which fails if the merchant is not approved. It is the interface contract between the two developers, and the only place a merchant's status blocks a payment.

Gto write
partners/mod.rs

Merchant domain types and errors, including the service mode that distinguishes physical, online, or both.

Gto write

backend/crates/core/src/funding/ · audit/ · corrections/ · reporting/

Funding, tracing, correcting, reporting

Four modules with no functional relation, brought together by what they do to the ledger: one writes new money into it, one writes alongside it, one corrects without erasing, and one only reads.

funding/topup.rs

The top-up: an operation from the MINISTRY_ISSUANCE system account to the member of staff's account. This is the only place money enters the system, and the issuance account's negative balance measures the total issued.

Sto write
funding/batch.rs · csv.rs

Bulk import of a payroll file, with a file digest to refuse a duplicate upload and rejection of the whole batch if a single line is wrong. Cut: the single top-up demonstrates the same accounting mechanism, and the batch only adds file parsing.

Gcut
funding/repo.rs · mod.rs

Queries and types for top-ups.

Sto write
audit/mod.rs

Writing to the audit log — who did what, when, from which address. Append-only like the ledger: these are the two tables that cannot be rewritten, one for the money, one for the decisions.

Gto write
corrections/mod.rs

Compensation: correcting an error with an inverse operation that leaves both traces behind. It is the only correction possible in an immutable ledger — you do not cancel, you post the reverse. Designed and documented, not implemented.

Gcut
reporting/mod.rs

Read-only: a member of staff's balance and history, a merchant's receipts, the national dashboard. The wording is watched here — a merchant takes in money, they do not have a balance, because what they receive is not currency they could spend inside the system.

Gto write

backend/crates/api/src/

The HTTP layer: translate, never decide

Every file here transforms something: a request into a call, an error into a status, a domain type into JSON. None holds a business rule — that is what lets the domain be tested without a server, and the API be changed without touching the ledger.

foundation

api/src/main.rs

The starting point: reading the environment, the connection pool, mounting the router, graceful shutdown. Never runs migrations in production — a deployment that changes the schema by itself is a deployment that cannot be rolled back.

Gto write
api/src/state.rs

What every handler receives: the pool, the clock, the signing keys, the configuration. Everything sits behind reference counters, so the state clones at no cost on each request.

Gto write
api/src/error.rs

The table translating domain errors into HTTP codes. Its central rule is a negative one: never any SQL detail in a response. A database error becomes an anonymous 500, because a verbose error message is a map of the schema handed to whoever asks for it.

Gto write
api/src/openapi.rs

The machine-readable description of the API, served in development only. It is the contract the front end consumes without having to read Rust.

Gto write

extractors/ — what filters before the handler

extractors/auth.rs

The highest-return piece in the project. The expected role is carried by the parameter's type: a merchant-space handler that received an employee does not compile. Access control stops being a line you can forget to write and becomes a compile error.

Gto write
extractors/validated.rs

Deserialises then validates the shape of a request — length, pattern, presence. Never a business rule: "the balance is sufficient" is not checked here, but under lock, in the ledger.

Gto write
extractors/pagination.rs

The opaque cursor and the capped limit. Opaque because a readable cursor is a cursor a client will forge, and capped because an unbounded limit is an invitation to request a hundred thousand rows.

Gto write
extractors/api_client.rs

Authentication for HR systems, distinct from the one for humans: no cookie, no session, an identifier and a hashed secret. The employer is derived from the authenticated client and never from the URL path.

Gto write

middleware/ — what applies to everything

middleware/request_id.rs

Attaches an identifier to every request, present in the logs and in the error response. It is what lets a user report a problem and lets us find the exact trace.

Gto write
middleware/security_headers.rs

The headers the browser enforces and the server cannot otherwise impose, plus the refusal of cleartext traffic outside development.

Gto write
middleware/rate_limit.rs

Differentiated limits, because the exposed surfaces are not attacked the same way: sign-in is targeted per IP and per email address, short-code entry per merchant, the public surface far more strictly than the rest.

Gto write
middleware/admin_audit.rs

Automatically records every successful administrative action. Making it automatic rather than calling the audit log inside each handler removes the question "did we remember to trace this one?".

Gto write

dto/ — the exposure boundary

dto/employee.rs · partner.rs · admin.rs · catalog.rs · integration.rs

One file per space. Domain types are never serialised directly: a DTO is a decision about exposure, not a shortcut. The difference shows the day an internal field is added to the domain — with no DTO, it ships in the HTTP response that same day.

SGto write
dto/public.rs

The only type visible without authentication, where every field is an explicit decision. This is the file an unwanted field would leak through. Cut along with the public surface, pending confirmation of the specification.

routes/ — the five spaces

routes/mod.rs

Assembles the subtrees and the middleware stack. Frozen in the first hour: each developer fills their own route files without ever touching this one, which removes the project's most likely merge conflict.

Gto write
routes/auth.rs

Sign in and sign out. The only place a session cookie is set and cleared.

Gto write
routes/employee.rs

The member of staff's space: their balance, their history, creating and cancelling a payment token. Everything here is implicitly "me" — the account identifier comes from the session, never from a parameter, otherwise reading a colleague's balance would be one curl away.

Sto write
routes/partner.rs

The merchant's space: settle a token, review receipts, and replay a batch of payments taken while offline. The batch is the one place in the project where each line gets its own transaction — a failing line must never bring down the others.

Sto write
routes/catalog.rs

Merchant search, open to all three signed-in roles. The only shared space in the application.

Gto write
routes/admin.rs

The ministry's space: reviewing applications, top-ups, features, the dashboard, and audit-chain verification. It is the only route that can prove live that the ledger has not been altered.

Gto write
routes/integration.rs

The machine entry point for administrations' HR systems: a member of staff's balance from their staff number. Kept apart from the human spaces because it authenticates differently and is rate-limited differently.

Gto write
routes/public.rs

The unauthenticated shop window: featured merchants and the list of towns, cached and strictly rate-limited. Cut: absent from the specification, pending confirmation.

backend/crates/tests/tests/

The tests: what gets proved rather than asserted

A separate package and a workspace member. Sitting at the root of backend/, these files belonged to no package and Cargo never compiled them — a test that does not run is worse than no test, because it reassures.

tests/invariants.rs

One test per invariant, against a real PostgreSQL — necessarily, since half the guarantees are carried by the schema rather than the code. This is the project's checkpoint: until it passes, nothing else gets built on top.

Swritten
tests/common/mod.rs

The fixtures: an employer, a member of staff with an account, an approved merchant, a top-up, a token, a settlement. Without them every test would restart forty lines of inserts, and nobody would write a tenth of them.

Swritten
tests/payments_flow.rs

The complete journey and its failures: insufficient balance, suspended merchant, cancelled token, closed account. Proves that the happy path works and that the refusals are the right ones.

Sto write
tests/degraded_mode.rs

The offline merchant: a token verified without network, a settlement replayed later, a duplicate in the queue, a token that lapsed in the meantime. This is the file that demonstrates the hardest requirement in the specification.

Sto write
tests/rbac.rs

Each space refuses foreign roles. The type system already makes the mistake impossible to write; this test checks that the response is a clean 403 and not an internal error.

Gto write
tests/public_surface.rs

Checks that no field outside the list, no unapproved merchant and no cookie appear on the public surface. Cut along with it.

backend/crates/worker/ · backend/deploy/

What runs without us, and what ships it

The two blocks cut entirely for the hand-in, each with an argument to give rather than a silence.

worker/src/main.rs

Three loops: token expiry every minute, forfeiting closed balances daily, chain verification hourly. Cut — expiry is handled lazily on each balance read, which gives the user the same visible result.

Gcut
deploy/Dockerfile · docker-compose.yml · Caddyfile

Image build, service orchestration and TLS termination. Cut: the demonstration runs on cargo run against a local PostgreSQL. The compose file stays useful for bringing up the database alone.

build order

Why the files get filled in this order

This is not a task list, it is a dependency chain: each step needs the previous one to be true. Step 4 is the checkpoint — a ledger whose invariants are not proved makes everything built on top of it worthless.

02core: ids, money, clock, error, config — the types everything handlesdone
03core/ledger: hash, repo, mod, balance — the only door to moneydone

05core/crypto: password, token_sig, short_code — no signature, no tokencurrent
06core/identity + api/extractors/auth.rs — no identity, no spacesahead
07core/payments: authorize, settle — the functional coreahead
08tests/payments_flow.rs, degraded_mode.rs — proof of the degraded modeahead
